## คำถามของงานนี้

index สำหรับค้นหาเวกเตอร์แบบประมาณ (ANN) อย่าง IVF-Flat และ HNSW ค้นได้เร็วกว่าการค้นแบบตรงทุกตัว (Flat) มาก แต่ต้องเสียเวลาสร้าง index ก่อน งานนี้เป็นโปรเจกต์วิจัยในรายวิชา ตั้งใจหาคำตอบว่า **ต้องค้นกี่ครั้ง ANN จึงจะคุ้มกว่า Flat** เมื่อนับเวลาสร้าง index รวมเข้าไปด้วย และตัวเลขนี้เปลี่ยนไปอย่างไรตามขนาดข้อมูลและจำนวนมิติ

## ขอบเขตการทดลอง

- **ข้อมูล:** ชุดข้อมูลรีวิวสินค้าสาธารณะ ทำความสะอาดและตัดข้อความซ้ำ แล้วแยก query สำหรับ validation และ test ชุดละ 1,000 รายการ
- **Embedding:** MiniLM-L6 (384 มิติ) และ mpnet-base (768 มิติ) ใช้ CPU อย่างเดียว ผลที่ได้จึงเป็นการเทียบ "โมเดล + index" ไม่ใช่ผลของจำนวนมิติล้วน ๆ
- **ขนาด corpus:** 10k, 50k, 100k, 250k, 500k และ 1M เวกเตอร์ ทุกขนาดเป็นส่วนหน้าของชุดเดียวกัน ผลแต่ละขนาดจึงเทียบกันได้
- **Index (FAISS):** Flat (exact), IVF-Flat (`nlist` ตามขนาดข้อมูล ไล่ `nprobe`) และ HNSW (`M=32`, `efConstruction=200` ไล่ `efSearch`)
- **การวัด:** latency ของ query ทีละรายการ (p50/p95/mean), Recall@10 เทียบกับ ground truth ที่คำนวณแบบ exact, เวลาสร้าง index และ peak RAM ของ process

ค่าพารามิเตอร์ที่ใช้ของแต่ละ index เลือกจาก **validation recall** เท่านั้น คือเลือกค่าที่ถูกที่สุดที่ได้ recall ≥ 0.95 แล้วค่อยรายงานผลบน test set เพื่อไม่ให้ใช้ test set ไปจูนพารามิเตอร์

## การออกแบบตัว benchmark

ตอนแรกออกแบบให้รันบนหลายเครื่องด้วยข้อมูลชุดเดียวกัน จึงมีส่วนที่ช่วยให้ผลเชื่อถือได้และรันต่อได้เมื่อหยุดกลางทาง

- **1 งาน = 1 subprocess:** ถ้างานไหน crash หรือใช้ RAM เกิน งานอื่นไม่เสียหาย และวัด peak RAM ของงานนั้นได้ตรง ๆ
- **บันทึกผลทันที:** เขียน CSV แบบ append + fsync ทุกครั้งที่จบงาน และมี journal ไว้กู้สถานะ รันใหม่ก็ข้ามงานที่เสร็จแล้วได้
- **Memory watchdog:** ตรวจ RAM ทุก 0.2 วินาที และข้ามงานที่ประเมินแล้วว่า RAM ไม่พอ
- **ตรวจความถูกต้องของข้อมูล:** ทุกไฟล์มี SHA-256 ใน manifest และตรวจ checksum ก่อนเริ่มรัน ค่า hash ของแต่ละงานรวมพารามิเตอร์ เวอร์ชัน FAISS/NumPy และ fingerprint ของข้อมูลไว้ด้วย
- **Unit tests:** ครอบคลุมการคำนวณ ground truth, recall, การเขียน CSV ตอน crash, สูตร break-even และการสร้าง index แบบ streaming

## สูตรจุดคุ้มทุน

เวลารวมเมื่อค้น Q ครั้ง คือ `T(Q) = เวลาสร้าง index + Q × latency เฉลี่ย`
จุดคุ้มทุน `Q*` คือจำนวน query ที่ทำให้ `T(Q)` ของ ANN เท่ากับของ Flat ถ้าค้นมากกว่า `Q*` ครั้ง ANN จะคุ้มกว่า

กราฟด้านบนสุดของหน้านี้คือ `T(Q)` ที่ 1M เวกเตอร์ 384 มิติ จุดที่เส้นตัดกันคือจุดคุ้มทุน IVF-Flat คุ้มกว่า Flat ที่ประมาณ 613 query ส่วน HNSW ที่ประมาณ 5,285 query

## ผลการทดลอง

รันบนโน้ตบุ๊กเครื่องเดียว (Intel Core 5 120U, RAM 16 GB) โดยสร้าง index ด้วย 4 threads และค้นด้วย 1 thread ผลด้านล่างเป็นที่ recall@10 ≥ 0.95

| 1M เวกเตอร์, 384 มิติ | เวลาสร้าง index | latency เฉลี่ยต่อ query | จุดคุ้มทุน |
|---|---|---|---|
| Flat (exact) | ~1.6 วินาที | ~143 ms | — |
| IVF-Flat | ~86 วินาที | ~4.1 ms | ~613 query |
| HNSW | ~751 วินาที | ~0.8 ms | ~5,285 query |

สิ่งที่เห็นจากผล

- ในการทดลองนี้ IVF-Flat คุ้มทุนเร็วกว่า คือประมาณ 160–610 query ส่วน HNSW ต้องประมาณ 1,400–6,000 query เพราะสร้าง index นานกว่ามาก
- แต่ถ้าค้นจำนวนมาก HNSW ตอบเร็วที่สุด ที่ 1M เวกเตอร์เร็วกว่า Flat ประมาณ 180 เท่า
- ถ้าแค่ค้นไม่กี่ร้อยครั้งแล้วเลิกใช้ Flat ยังคุ้มกว่าแม้มีข้อมูลระดับล้านเวกเตอร์

## ข้อจำกัด

- รันจริงบนเครื่องเดียว ยังไม่ได้เทียบข้ามเครื่องตามที่ออกแบบไว้
- ทำได้แค่ 384 และ 768 มิติ เพราะโมเดลที่ให้ 1536 มิติช้าเกินไปบน CPU (จากที่วัดไว้ mpnet-768 ก็ต้องใช้เวลาประมาณ 54 ชั่วโมงสำหรับข้อความ 1 ล้านรายการแล้ว)
- ที่ 768 มิติ ขนาด 1M ไม่มีจุดคุ้มทุน เพราะ Flat ใช้ RAM เกินจนรันไม่ได้ ส่วนขนาด 500k ไม่ได้คำนวณ เพราะ recall บน test ได้ต่ำกว่า 0.95 เล็กน้อย (0.94–0.95) และรอบที่ 3 ของ Flat/IVF-Flat ที่ขนาดนี้ RAM ไม่พอ
- latency ทั้งหมดวัดแบบ query ทีละรายการด้วย 1 thread ไม่ได้วัดแบบ batch
