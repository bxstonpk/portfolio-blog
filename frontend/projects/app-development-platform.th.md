## ภาพรวม

ระบบนี้คือมาตรฐานการพัฒนาแอปภายในของบริษัทตั้งแต่ต้นน้ำ เริ่มตั้งแต่พนักงานคิดจะทำแอป ไปจนแอปขึ้นใช้งานจริงและมีคนดูแลต่อ ไม่ได้เป็นแค่เครื่องมือ deploy

พนักงานสร้างแอปด้วย Claude Code โดย Claude ทำตาม skill ของบริษัท และคุยกับแพลตฟอร์มผ่าน MCP server ช่องทางเดียว กติกาทุกข้อ เช่น ต้องลงทะเบียนก่อน ต้องใช้ stack ตามมาตรฐาน ห้ามใช้ library ต้องห้าม ต้องผ่านเทสต์ และต้องมีคนเซ็นก่อนขึ้น production ถูกบังคับที่ฝั่ง server ทั้งหมด ไม่ได้อาศัยแค่การขอให้ Claude ทำตาม

**ปัญหาที่แก้:** ก่อนหน้านี้พนักงานใช้ Claude Code สร้างแอปด้วยเทคโนโลยีอะไรก็ได้ แล้วส่งให้ IT นำขึ้นทีละแอปด้วยมือ ผลคือไม่มีมาตรฐาน ความปลอดภัยขึ้นกับคนที่ทำ ไม่มีทะเบียนว่ามีแอปอะไรบ้าง ใครเป็นเจ้าของ และงานของ IT ก็เพิ่มตามจำนวนแอป

ระบบใช้ภายในองค์กรเท่านั้น รันบน Linux server เครื่องเดียวที่มี Docker เข้าถึงได้จาก LAN ของบริษัท ผมพัฒนาช่วง ส.ค. – ต.ค. 2569 เริ่มจากเขียน BRD, requirements, สถาปัตยกรรม และ decision log ก่อน แล้วจึงลงมือเขียนระบบ

## 1. ตั้งค่าเครื่องพนักงาน

- พนักงานรันตัวติดตั้งคำสั่งเดียว ตัวติดตั้งจะลง MCP server, skill และ template ของบริษัทให้ Claude Code
- พนักงานลงทะเบียนบัญชีด้วยรหัสลงทะเบียนจาก IT จากนั้นแต่ละเครื่องต้องขอ API key ของตัวเอง และเจ้าของบัญชีต้องกดอนุมัติใน Portal ก่อนใช้งาน
- เมื่อแพลตฟอร์มออกเวอร์ชันใหม่ เครื่องที่ยังเป็นเวอร์ชันเก่าจะถูกปฏิเสธจนกว่าจะอัปเดต Claude จะรันคำสั่งอัปเดตให้เอง เพื่อให้ทุกเครื่องใช้กติกาชุดเดียวกัน

## 2. เริ่มแอปใหม่: ลงทะเบียนก่อนเขียนโค้ด

ก่อนเขียนโค้ดบรรทัดแรก Claude จะอ่านมาตรฐานจากแพลตฟอร์ม (`get_standards`) แล้วถามพนักงานว่า

- แอปนี้ทำอะไร ใครใช้ ประมาณกี่คน
- เก็บข้อมูลส่วนบุคคลไหม ถ้าเก็บ เก็บอะไรบ้าง
- API จะใช้ภาษาอะไร (Python, Node.js, TypeScript หรือ Go)

จากนั้นลงทะเบียนแอปพร้อม profile นี้ (`start_project`) การเริ่มแอปไม่ต้องรออนุมัติ แต่แอปที่ไม่มี profile จะ build ไม่ได้ Claude ถูกกำหนดให้ถามเสมอ ห้ามเดาวัตถุประสงค์ของแอป หรือเดาว่ามีข้อมูลส่วนบุคคลหรือไม่

## 3. สร้างโครงจาก template ของบริษัท

`scaffold_project` สร้างโปรเจกต์จาก template มาตรฐาน มี React frontend, API ในภาษาที่เลือก, `deployment.yaml`, `REVIEW.md` ที่รอเติม และ `STANDARD.md` ที่อธิบายข้อตกลงของบริษัท เช่น API ต้องฟังพอร์ตจาก `$PORT` และอ่านค่าฐานข้อมูลจาก environment

แอปใหม่จะถูก deploy ขึ้น **ตัว dev** ทันที และพนักงานได้ลิงก์เปิดดูได้เลยระหว่างที่ Claude เขียนต่อ ตัว dev มีฐานข้อมูล MySQL และ address ของตัวเอง

## 4. ระหว่างพัฒนา: ตรวจตามมาตรฐานไปพร้อมกัน

- **ดูแอปบน server เสมอ:** ทุกครั้งที่แก้ Claude จะ deploy ขึ้นตัว dev แล้วส่งลิงก์เดิมให้ ข้อมูลที่พนักงานกรอกไว้ยังอยู่ พนักงานไม่ต้องติดตั้ง Node, Go หรือ Python ในเครื่อง และไม่ต้องรันแอปในเครื่องเอง
- **ตรวจระหว่างเขียน:** `check_project` ใช้ตัวตรวจ dependency ตัวเดียวกับตอน build ตรวจทั้ง profile, `REVIEW.md` และคำขอยกเว้นที่ค้างอยู่
- **เทสต์บนแพลตฟอร์ม:** `run_tests` รันเทสต์ของแต่ละ service ใน sandbox (`go vet`, `go test`, `pytest`, npm `build`/`test`) ถ้า service ไหนไม่มีเทสต์ รายงานจะบอกตรง ๆ ว่ายังไม่ได้ทดสอบ
- **นอกมาตรฐานต้องขอก่อน:** ถ้าต้องใช้ library หรือเทคโนโลยีที่ไม่อยู่ในมาตรฐาน Claude ต้องบอกพนักงานก่อน แล้วจึงส่งคำขอยกเว้นพร้อมเหตุผล Admin เป็นคนตัดสินในหน้า Standards ระหว่างที่ยังไม่อนุมัติ library ต้องห้ามจะทำให้ build ไม่ผ่าน
- **แยกข้อมูลทดสอบ:** ข้อมูลที่ Claude ใส่ลงตัว dev เองจะถูกบันทึกว่าเป็นข้อมูลทดสอบ จะได้ไม่ถูกเข้าใจว่าเป็นข้อมูลจริง

![หน้า Standards ของ Admin: คำขอยกเว้นที่รอตัดสิน และ library ที่บริษัทไม่อนุญาต (ข้อมูลจำลอง)](images/projects/app-development-platform/standards.webp)

## 5. ขอขึ้น production: ตรวจทุกไฟล์และเซ็นอนุมัติ

production เป็นขั้นแยก ทำเมื่อพนักงานขอเท่านั้น และต้องผ่านด่านเหล่านี้

- **REVIEW.md:** Claude เขียนเป็นภาษาไทยจากโค้ดจริง ครอบคลุมแอปทำอะไร workflow จากหน้าเว็บผ่าน API ไปถึงฐานข้อมูล path และหน้าที่ของทุกไฟล์ ข้อมูลที่เก็บ ชื่อ config/secret ที่ใช้ (ไม่ใส่ค่า) สิ่งที่เปลี่ยน เทสต์ที่รัน และความเสี่ยง ถ้าไม่มีไฟล์นี้ ระบบปฏิเสธตั้งแต่ก่อน build
- **เทสต์และสแกน:** รันเทสต์ซ้ำบน source ชุดที่จะ build จริง และทุก image ต้องผ่านการสแกน Trivy ระดับ CRITICAL
- **ข้อมูลจากตัว dev:** การขึ้น production ครั้งแรกจะถามพนักงานว่าข้อมูลในตัว dev เป็นข้อมูลจริงที่ต้องการเก็บไว้ไหม Claude ห้ามตัดสินใจเรื่องนี้เอง
- **เซ็นอนุมัติ:** Admin เปิดหน้าอนุมัติ ระบบดาวน์โหลด source มาตรวจ hash แล้วให้อ่านทุกไฟล์ จากนั้น Admin เซ็นด้วย Ed25519 private key ที่ถืออยู่คนเดียว ลายเซ็นครอบคลุม image, source, ผลเทสต์ และ REVIEW.md ลายเซ็นปลอมหรือลายเซ็นเก่าที่นำมาใช้ซ้ำจะถูกปฏิเสธ

![หน้าอนุมัติ production: ตรวจ source อ่าน REVIEW.md ผลเทสต์ และผลสแกน image ก่อนเซ็น (ข้อมูลจำลอง)](images/projects/app-development-platform/approval.webp)

## 6. หลังใช้งาน: แพลตฟอร์มดูแลต่อ

- **Deploy:** health check ก่อนปล่อย traffic deploy ใหม่ไม่ทำให้เวอร์ชันที่ใช้อยู่ล่ม และถ้าเวอร์ชันใหม่พังซ้ำ ๆ จะ rollback อัตโนมัติ
- **Scale-to-zero:** แอปที่ไม่มีคนใช้จะหยุด แล้ว request แรกจะปลุกขึ้นมาที่ address เดิม ฐานข้อมูลก็หลับไปพร้อมแอป
- **Backup:** full ทุกวันอาทิตย์ differential จันทร์ถึงเสาร์ เข้ารหัสด้วยกุญแจของแพลตฟอร์ม เจ้าของแอป restore เองได้
- **Log และ metrics:** เก็บ log 90 วันโดยซ่อนค่า secret และวัด CPU, memory, request, error และ latency เอง แจ้งเตือนเมื่อเกินเกณฑ์
- **Dashboard ของ Admin:** ดูทั้ง server และทุกแอปเหมือน Task Manager ระงับแอปที่มีปัญหาได้พร้อมเหตุผล และมีแค่ Admin ที่เปิดกลับได้
- **Audit log:** แบบ hash-chain ที่เขียนต่อท้ายได้อย่างเดียว

## ส่วนประกอบของระบบ

| ส่วน | ภาษา | หน้าที่ |
|---|---|---|
| Company Deployment Skill + templates | Markdown | ขั้นตอนที่ Claude ต้องทำตั้งแต่เริ่มแอปจนขึ้น production, schema ของ `deployment.yaml` และโค้ดตั้งต้นของแต่ละภาษา |
| MCP server + CLI | Python | เครื่องมือ 34 ตัวที่ Claude ใช้ ทั้งมาตรฐาน (start, scaffold, check, exception) เทสต์ ตัว dev deploy log และ metrics รวมถึง CLI ของผู้อนุมัติ |
| Platform API | Go | ตัวเดียวที่แตะ PostgreSQL และ Docker ตรวจสิทธิ์ บังคับกติกา build สแกน และรันแอป |

## เอกสารและการทดสอบ

- **เอกสาร:** BRD, functional/non-functional requirements, สถาปัตยกรรม, SDLC, risk register และ decision log (30 ข้อ) รวมถึงเอกสารมาตรฐานฝ่าย IT ภาษาไทยสำหรับพนักงาน
- **Unit test:** Go 391 ฟังก์ชัน, Python 155 และ Portal 109 test case
- **Script ตรวจกับระบบจริง:** รันกับ stack ที่ทำงานอยู่ ครอบคลุม
  - เริ่มแอปตามมาตรฐาน: scaffold, library ต้องห้ามถูกปฏิเสธ และ exception
  - เทสต์บนแพลตฟอร์ม และตัว dev ที่ข้อมูลไม่หาย
  - deploy React + API ทุกภาษา + MySQL จาก template ไปจนใช้งานได้จริงใน browser
  - เครื่องมือ MCP ทั้ง 34 ตัวผ่าน stdio
  - ลายเซ็นอนุมัติ และ backup/restore

## สิ่งที่ยังไม่มี

- แจ้งเตือนอยู่ใน Portal อย่างเดียว ยังไม่ส่งออกอีเมลหรือแชต
- ยังหมุนกุญแจเข้ารหัสไม่ได้ และ script ของ TPM ทดสอบกับ software TPM เท่านั้น
- ทุกอย่างอยู่บนเครื่องเดียว ไม่มี high availability และ backup อยู่เครื่องเดียวกับฐานข้อมูล
- ยังไม่มีระบบรีเซ็ตรหัสผ่าน และ exception แบบ stack/other เป็นแค่การบันทึกการตัดสินใจ ระบบยังไม่บังคับเอง
